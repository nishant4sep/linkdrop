# P1.2 — hardening checkpoint

## Added

- Atomic approval/rejection RPC: locks the submission, verifies the administrator allowlist, creates a published resource when approving, changes submission state, and appends review history in one transaction.
- Append-only moderation review history with reviewer, decision, note, and resource reference.
- Partial unique indexes preventing duplicate pending submissions and duplicate published URLs per post.
- Shared database-backed fixed-window rate limiting for authenticated submissions and public resolution.
- Updated API handlers to use the RPC and limiter.

## Required schema verification

The migration assumes these columns exist with compatible types:

- `submissions`: `id`, `post_id`, `submitted_by`, `resource_url`, `normalized_resource_url`, `resource_type`, `description`, `status`, `created_at`
- `resources`: `id`, `post_id`, `resource_url`, `resource_type`, `description`, `status`, `created_at`
- `posts`: `id`, unique `canonical_url`
- `admin_users`: `user_id`, `disabled_at`

It also assumes `pending`, `approved`, `rejected`, and `published` are valid state values. Check the actual P0 schema before applying. If it differs, adapt the migration and route contracts together.

## Operational cautions

- The resolver limiter is per normalized Instagram post code, so it limits repeated requests for one post but does not stop an attacker rotating many post codes. Add provider-level edge/WAF limits and monitoring before launch.
- The limiter table needs periodic cleanup of expired rows. Add a scheduled cleanup job or partition/retention strategy before meaningful traffic.
- Do not trust client-supplied forwarding headers for IP rate limiting. If adding IP limits, use only the hosting provider's documented trusted proxy mechanism.
- The approval RPC uses the authenticated admin ID supplied by the server route and independently checks the current admin allowlist. The service-role key must remain server-only.
- Append-only triggers protect application paths, not a database owner with permission to disable triggers. Restrict database operator access and maintain backups.
- URL syntax validation is not destination verification. No arbitrary destination fetches are performed by these routes.

## Tests to run before launch

1. Apply migrations on a disposable development database.
2. Confirm a contributor cannot execute the RPC through the public API role.
3. Confirm a non-admin user cannot approve even if a request is manually crafted.
4. Submit the same post/resource concurrently and verify the unique indexes prevent duplicates.
5. Approve the same submission concurrently and verify only one transaction succeeds.
6. Force an insert constraint failure during approval and verify neither status nor review history is partially committed.
7. Verify rejection produces no public resource.
8. Verify the resolver returns published resources only.
9. Exhaust the limiter and verify a 429 with Retry-After; simulate a limiter outage and verify mutation endpoints fail closed.
10. Confirm logs contain no bearer tokens, service-role keys, or private submission evidence.

This checkpoint has not been executed against a live project. Treat it as implementation source that requires migration review, automated tests, and deployment validation.
